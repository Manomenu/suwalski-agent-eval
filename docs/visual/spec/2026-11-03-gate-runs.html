Bramkowy run AC: suwageval gate

Status: approved Data: 2026-11-03 Branch: master Rozmiar: L (nowa funkcja + kontrakt YAML)

TL;DR

Scenariusz może być guardrailem kryterium akceptacji: sekcja acGuardrail: { id: AC-refunds-1 } w jego YAML-u. Komenda suwageval gate uruchamia wszystkie takie scenariusze agenta, a każdy zalicza pierwsza udana próba (domyślnie do 5 prób). Wynikiem nie jest raport z pass rate'ami, tylko odpowiedź tak/nie w CLI: przy sukcesie jedna linia, przy porażce pełny opis tego, co padło. Bramka zatrzymuje się na pierwszym AC, które wyczerpie próby, i kończy kodem ≠ 0. To narzędzie dla CI agenta i dla agenta w Claude Code. Web jej nie pokazuje.

Stan bez bramki

suwageval run to run ewaluacyjny: każdy scenariusz leci samples razy (domyślnie 3), a check przechodzi, gdy jego pass rate osiąga passThreshold. Wynikiem jest raport z regresjami względem poprzednich runów. Tryb świetnie sprawdza się przy mierzeniu jakości. Na bramce przeszkadza:

  • nie da się powiedzieć, które scenariusze pilnują kryteriów akceptacji: scenariusz nie ma powiązania z id AC ze specki;
  • run zawsze przechodzi wszystkie scenariusze i wszystkie sample, a CI chce tylko odpowiedzi „przeszło / nie przeszło” i powodu;
  • semantyka „pass rate ≥ próg” nie pasuje do bramki: tu chcemy wiedzieć, czy agent potrafi spełnić kryterium, z kilkoma podejściami na niedeterminizm modelu.

Cele

Cele

  • Scenariusz deklaruje, którego AC jest guardrailem (acGuardrail.id), opcjonalnie z własnym limitem prób.
  • suwageval gate uruchamia każdy scenariusz z acGuardrail, scenariusz zalicza pierwsza udana próba, a bramka staje na pierwszym AC, które wyczerpało próby.
  • Ciche wyjście do logu CI i kod wyjścia; --json dla agenta.
  • Ta sama walidacja acGuardrail w validate i na serwerze.
  • Plugin Claude Code opisuje komendę, więc agent może sam puścić bramkę i odczytać wynik.

Poza zakresem optional

  • Jakikolwiek widok bramki w webie: lista, filtr czy strona. Bramka żyje w CI, a lokalnie testuje się zwykłym run.
  • Zawężanie bramki tagami (--tag): o udziale decyduje wyłącznie sekcja acGuardrail.
  • Push w ramach gate: najpierw suwageval push, jak przed run.
  • Regresje, trend i ponowna ocena (recheck) runu bramkowego.
  • Sprawdzanie, czy id AC istnieje w specce agenta: Suwageval nie zna repozytorium specek.
  • Wyzwalacze CI (PR, merge): osobny punkt TODO „Runs from an agent's CI”.

Scenariusze

1. CI agenta suwexag po zmianie promptu: wszystko przechodzi

Agent ma 13 scenariuszy, z czego 5 ma acGuardrail (AC-refunds-1…5). agent.yaml nie ustawia limitu, więc domyślny wynosi 5.

$ suwageval push && suwageval gate PASSED 5 of 5 acceptance criteria $ echo $? 0

2. Ta sama bramka, AC pada

AC-refunds-2 (retryLimit: 2) nie przechodzi w żadnej z prób. Log CI mówi, co padło w każdej próbie i co agent zrobił w ostatniej.

$ suwageval gate FAILED AC-refunds-2 (scenario refund-not-delivered): 2 of 2 attempts failed attempt 1: no-refund-when-shipped: refund_order (by support) was not called in turn 1. attempt 2: no-refund-when-shipped: refund_order (by support) was not called in turn 1. what the agent did in the last attempt: tool call get_order {"order_id":"A-18"} tool result: {"orderId":"A-18","status":"shipped",…} assistant: Sorry — order A-18 is still shipped, not delivered yet, so I can't refund it… FAILED AC-refunds-2 (4 of 5 acceptance criteria passed); everything: suwageval results 243d… $ echo $? 1

3. Agent w Claude Code sprawdza swoją zmianę

Claude zmienił narzędzie refundów w repo agenta. Plugin podpowiada mu suwageval push i suwageval gate --json. Z gate.failedGuardrail i komunikatów checków agent odczytuje, co padło, poprawia kod i puszcza bramkę jeszcze raz.

4. Błędne id w scenariuszu

Autor wpisał acGuardrail: { id: refunds-1 } i drugi scenariusz z tym samym AC-refunds-1. suwageval validate zgłasza oba problemy przy plikach. Push odrzuca te same błędy na serwerze tą samą regułą.

Zachowanie

Reguły

  • Udział: w bramce biorą udział dokładnie te scenariusze agenta na serwerze, które mają sekcję acGuardrail. Bramka czyta to, co jest na serwerze, więc wcześniej trzeba zrobić suwageval push (mówi to --help). Scenariusze z acGuardrail dalej wchodzą do zwykłych runów.
  • Próba to jedna rozmowa scenariusza (z symulacją, jeśli ją ma), oceniona wszystkimi checkami scenariusza. Przechodzi, gdy przeszedł każdy check. samples i passThreshold bramka ignoruje.
  • Limit prób: acGuardrail.retryLimit scenariusza, potem acGuardrailRetryLimit z agent.yaml (z chwili startu bramki), potem 5. Liczba oznacza maksymalną liczbę prób, w zakresie 1–20.
  • Zatrzymanie: na pierwszym AC, które wyczerpało próby. Scenariusze, które jeszcze nie ruszyły, nie są wywoływane. Te, które już trwają (scenariusze idą równolegle w limicie serwera), kończą bieżącą próbę i nie zaczynają kolejnej.
  • Wyjście (quiet): sukces to jedna linia PASSED n of n acceptance criteria. Dla każdego AC, które padło, wydruk podaje każdą próbę z checkami, które nie przeszły, i powodem werdyktu (albo błąd agenta), a potem przebieg ostatniej próby (wywołania narzędzi, wyniki, odpowiedź). Dalej idą AC zatrzymane w trakcie, niezaczęte scenariusze i linia końcowa z id runu. --json wypisuje pełne wyniki z werdyktem w gate.
  • Run bramkowy to werdykt, nie ewaluacja: serwer go wykonuje i przechowuje, ale nie pokazuje go żadna lista ani strona weba, suwageval runs, historia regresji, trend, problemy ani liczniki runów wersji. Czyta go tylko gate (i results <id>). Nie da się zrobić jego rechecku: bramkę puszcza się jeszcze raz.

Decyzje optional

Bramkę wykonuje serwer, tak jak run, a nie CLI lokalnie. Sędzia, symulator i modele siedzą na serwerze, a kolejka workera potrzebuje rekordu runu. W CI serwer i jego baza żyją tylko przez czas joba.

Bramka bierze każdy scenariusz z acGuardrail, bez --tag. O tym, co jest guardrailem, decyduje plik scenariusza, a nie wywołanie w CI, więc nie da się po cichu pominąć AC.

Bramka nie robi pusha. Jest spójna z run, a push ma własny raport błędów; --help mówi, że push idzie pierwszy.

Bramka jest tylko w CLI, z cichym wyjściem. Przy sukcesie nikt nie czyta logu, przy porażce log musi wystarczyć do zrozumienia, co padło. Liczniki checków i pasek postępu runu nie opisują dobrze bramki, więc web jej nie pokazuje.

Format id AC-<feature>-<n> jest wymuszany tak jak w metodzie spec-driven, żeby id w scenariuszu było tym samym id, co w specce agenta. Reguła żyje raz, w Suwageval.Contracts, i używają jej CLI i serwer.

Recheck runu bramkowego jest zablokowany. Próby urwały się na pierwszym sukcesie albo failu, więc ponowna ocena nie odpowiada na pytanie bramki.

Kryteria akceptacji

  • AC-gate-runs-1 validate przyjmuje scenariusz z sekcją acGuardrail (id w formacie AC i retryLimit: 2) i agent.yaml z acGuardrailRetryLimit: 3, a odrzuca id spoza formatu AC-<feature>-<n>, brak id, retryLimit spoza 1–20 oraz scenariusz z acGuardrail bez checków.
  • AC-gate-runs-2 validate zgłasza to samo id AC w dwóch scenariuszach agenta jako błąd, z nazwami obu plików.
  • AC-gate-runs-3 Serwer odrzuca push scenariuszy, które łamią którąkolwiek z reguł acGuardrail (format id, unikalność, zakres limitu), tym samym komunikatem, który podaje validate (422, nic nie zostaje zapisane).
  • AC-gate-runs-4 suwageval gate uruchamia dokładnie scenariusze agenta z acGuardrail. Scenariusze bez sekcji nie są wywoływane.
  • AC-gate-runs-5 Scenariusz zalicza pierwsza próba, w której przeszły wszystkie checki. Po niej nie startuje żadna kolejna próba tego scenariusza, niezależnie od samples i passThreshold.
  • AC-gate-runs-6 Limit prób to acGuardrail.retryLimit, a bez niego acGuardrailRetryLimit z agent.yaml, a bez niego 5. Scenariusz, który nie przechodzi nigdy, dostaje dokładnie tyle prób, ile wynosi ten limit.
  • AC-gate-runs-7 Gdy AC wyczerpie próby, bramka się kończy. Scenariusze, których próby jeszcze się nie zaczęły, nie są wywoływane. gate kończy się kodem 1.
  • AC-gate-runs-8 gate kończy się kodem 0, gdy każde AC przeszło, a kodem 2, gdy agent nie ma scenariuszy z acGuardrail, któryś nie ma checka, walidacja nie przeszła albo run się nie skończył.
  • AC-gate-runs-9 Wyjście gate jest ciche: przy sukcesie to jedna linia PASSED n of n acceptance criteria. Dla każdego AC, które padło, podaje każdą próbę z checkami, które nie przeszły, i ich komunikatem, potem przebieg ostatniej próby i linię końcową z id runu. --json zwraca wyniki z werdyktem w gate.
  • AC-gate-runs-10 Run bramkowy nie pojawia się na żadnej liście runów (web i suwageval runs, przy każdym filtrze), w trendzie, w problemach ani w licznikach runów wersji.
  • AC-gate-runs-11 Na stronie runu karta scenariusza z acGuardrail pokazuje jego id AC.
  • AC-gate-runs-12 Plugin opisuje suwageval gate (skill suwageval, skill /suwageval:run): kiedy go użyć, że najpierw idzie push, jak czytać kody wyjścia i --json. Komenda ma też wiersz w docs/front-doors.md.

Ryzyka i założenia

Koszt przy niestabilnym AC: 10 scenariuszy × 5 prób × symulacja wielu tur to dużo wywołań agenta i sędziego. Ograniczają to zatrzymanie na pierwszym failu i limit 1–20; scenariusze AC warto trzymać krótkie.

„Pierwsza udana próba” przepuszcza niestabilne zachowanie, np. AC przechodzące w 1 na 5 prób. To świadomy wybór bramki (agent potrafi). Stabilność mierzy zwykły run z samplami i passThreshold.

Runy bramkowe zostają w bazie, niewidoczne. W CI baza żyje tylko przez czas joba. Na stałym serwerze runy bramkowe się zbierają: znikają razem z wersją lub agentem, ale nie mają własnego sprzątania.
