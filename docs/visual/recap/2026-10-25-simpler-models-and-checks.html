Jak to działa

Elementy i ich role

ModelClients.EntryFor

Jedna reguła dla każdej roli: jej własny wpis, a bez niego fallback, a bez niego nic. Każdy wpis ma swoją pulę wywołań.

używają: Judge, ArgumentJudge, UserSimulator, UserDescriber

Chart: models

Mapa fallback / judge / simulator / describer, jeden helper renderuje zmienne Models__<nazwa>__* i envFrom sekretów. Live check renderuje się, gdy jest jakikolwiek model.

Validator: wymagane fixtures

Czyta required z najwyższego poziomu fixturesSchema agenta i porównuje z kluczami fixtures scenariusza. Głębiej nie sprawdza.

tylko online: offline nie zna kontraktu

Hook SessionStart

W repo z suwageval/agent.yaml dokłada do sesji pętlę: co pada → rozmowa jako scenariusz → run → dlaczego (z tracingiem projektu) → popraw agenta, nie test. Dopisuje, czy monitoring jest włączony i czy jest CLI.

Co się dzieje, gdy Claude otwiera sesję w repo suwexag

  1. hooks.json odpala session-context.sh przy starcie, /clear i kompaktowaniu.

  2. Skrypt widzi suwageval/agent.yaml, wypisuje agent-loop.md i linię „Monitoring is on”, bo plik ma features.monitoring.

  3. Claude Code dodaje to do kontekstu, więc na „agent źle odpowiada o zwrotach” Claude zaczyna od runs / monitoring checks, a nie od zgadywania.

  4. W repo bez suwageval/agent.yaml skrypt nic nie wypisuje: zero kosztu w innych projektach.
