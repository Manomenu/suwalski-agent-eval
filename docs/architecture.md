# Architecture

## Stack

- **Server:** .NET 10, ASP.NET Core minimal APIs, PostgreSQL through Npgsql and Dapper (SQL written by hand, numbered migrations), an OpenAPI document the web app is typed from; Microsoft Agent Framework for the judge and the user simulator.
- **Web:** React 19, Mantine, Vite, TypeScript strict.
- **Around them:** PostgreSQL 17, a container per part, compose for the whole stack on a laptop, a Helm chart with a post-deploy smoke test for the cluster.

The server is the one HTTP API: the web app and the CLI both use it, and Claude Code through the CLI; there is no MCP endpoint. The evaluation's routes live under `/api/eval/…`, the monitoring's under `/api/monitoring/…`, and what every area shares (agents, versions, `/api/health`) has no prefix. The agent under test is reached over HTTP through its two routes ([scenario-format.md](scenario-format.md)) and is never part of this repository's deployment.

## The map

One line per top-level path (at most 300 characters each). suwgate's `repository-layout` guard reads these lines: a new top-level folder needs its line here, a deleted one loses it.

- `Suwageval.slnx` — the .NET solution. Projects sit side by side at the root, each folder named like its project, with no separate source and test roots: the web app keeps tests beside its code.
- `Suwageval.Server/` — the HTTP API, cut into feature folders: `Api/` wires the routes, areas hold the product's features, and shared features stand below them. Migrations are numbered SQL, applied at start-up by grate, never edited.
- `Suwageval.Server.Tests/` — xUnit v3 tests against a real PostgreSQL, mirroring the server's folders. `EndToEnd/` is the one place where the CLI runs against the server in process. The SDK's tests live here too: it has no test project.
- `Suwageval.AgentSdk/` — the NuGet package of a .NET agent under test (`net9.0;net10.0`): the agent contract, the log items, the two endpoints and the monitoring.
- `Suwageval.Contracts/` — the records the API sends and receives and the CLI reads from YAML, with the rules that decide validity, so the CLI and the server cannot drift.
- `Suwageval.Cli/` — the `suwageval` command, a .NET tool (System.CommandLine, YamlDotNet). Code is cut into areas like the server's; command names stay flat; `suwageval --help` lists them by area.
- `Suwageval.Cli.Tests/` — the CLI's tests (xUnit v3), mirroring its folders; pure unit tests, no server and no database. `Sample/` is the one agent folder the tests use.
- `Suwageval.Gate/` — the gate's .NET half: one `SuwgateGuards.VerifyAll` test that runs every guard of Suwgate.Architecture and Suwgate.Database, and this repository's own guards suwgate does not have; `scripts/chart.sh`, a step of `suwgate.yml`. See "The gate" below.
- `Suwageval.Web/` — the web app (React, Mantine, Vite). `src/evaluation/` and `src/monitoring/` are areas with a folder per feature; the shared folders stand beside them. Practices: [web.md](web.md).
- `contract/` — `openapi.json`, the server's HTTP API as the CLI, the web and agents' tooling read it, generated by `just api-types`, with its version in `package.json`; the gate's `api-version` step (oasdiff) fails a break the version does not say.
- `deploy/` — the Helm chart the cluster runs: server, web, ingress, the post-deploy smoke test and the daily live check.
- `compose.yaml` — the whole stack on a laptop from the same Dockerfiles, no cluster needed.
- `Suwageval.Server/Dockerfile`, `Suwageval.Web/Dockerfile` — the two images; the build context is the repository root.
- `claude-plugin/` — the Claude Code plugin: skills and a session hook. Text and one shell script; the file format is linked from the skill, not copied.
- `.claude-plugin/` — `marketplace.json`, which makes this repository a plugin marketplace; Claude Code looks for it there.
- `docs/` — documentation: this map, `development.md`, `deployment.md`, `release.md`, `web.md`, the file format, the concepts and the front doors; specs in `visual/spec/`.
- `.claude/` — the committed Claude Code settings: `suwgate hook stop` and `suwgate hook guard-edit`.
- `scripts/` — `scripts/.internal/` holds everyday tools CI and `just` run; each answers `--help`.
- `.github/` — `workflows/ci.yml` (gate, browser tests, then images, published only from `master`) and `workflows/agent-sdk.yml` (the SDK release; a nuget.org policy names this file, so it is never renamed alone).
- `.githooks/` — `pre-commit` runs `suwgate hook pre-commit` (gitleaks on what is being committed, then the quick gate); `just sync` enables it.
- `.vscode/` — the editor's glue: recommended extensions, file nesting, launch configurations, no style rules.
- `.config/` — `dotnet-tools.json`: the pinned CSharpier.
- `.artifacts/` — everything generated (e2e reports, renders), outside git and the images.

Files at the root: `suwgate.yml` (the gate: profiles, the steps it adds, the exceptions with their reasons, the local stack), `layers.json` (the layers of the server and the CLI, and which project may reference which), `criteria.json` (the files the `criteria` step reads as prose), `Directory.Build.props` (target framework, warnings as errors, lock files, and Suwgate.Architecture, which brings the analyzers, the banned APIs and the rules), `Directory.Build.rsp` (no idle MSBuild workers), `Directory.Packages.props` (every package version, once), `.editorconfig` (whitespace, CSharpier's width and the rules this repository switches off), `.gitattributes` (a new binary or generated file type gets its line), `global.json`, `nuget.config` (nuget.org only), `tmux-dev.just` and `secrets.just` (modules of the `justfile`).

## The gate

The gate is [suwgate](https://github.com/Manomenu/suwgate): `suwgate check` runs the steps of the profiles `web`, `dotnet` and `database` and its repository guards, configured in `suwgate.yml`; the .NET guards come from the NuGet packages Suwgate.Architecture and Suwgate.Database, called from `Suwageval.Gate`. What every repository checks lives there, not here: this repository keeps only its configuration and the guards suwgate does not have.

- Belongs in the gate: anything that decides whether a change passes. A tool for everyday work stays in `scripts/`, even when the gate calls it.
- The edit hook (`suwgate hook guard-edit`) refuses an agent's edit of the gate files: `suwgate.yml`, `layers.json`, the tool configs, the workflows, `Suwageval.Gate/`. The owner lifts it for one session with `ALLOW_GATE_EDIT=1 claude`.
- An exception in `suwgate.yml` lets one target through one guard, always with its reason; one that no longer matches fails the gate.
- The SDK's layers stay beside the SDK's tests (`AgentSdkContractsTests` in `Suwageval.Server.Tests`): the release workflow picks those tests by class name, and its proof should be what it ran.

## What the gate forbids

Each line is a build rule, a guard or a test; its message says the fix. Rules live as low as they can: types and analyzers first.

- From suwgate: the build (analyzers `latest-all`, warnings as errors, style rules, namespace equals folder, NuGet audit, the banned APIs: the clock, blocking on tasks, `Console`, `Activator`, reflection discovery, Newtonsoft.Json), CSharpier and Prettier (`just fmt` fixes both), the tests, tsc strict, eslint (strict type-checked, no comments, no inline switches), knip, the API contract and its version, acceptance criteria, compose, shellcheck, gitleaks; the guards over comments, names, scripts, images, docs paths, the map above, AGENTS.md, VS Code settings, packages, appsettings and hooks; and, through Suwgate.Architecture, the server's layers, endpoints, project references, interfaces with two implementations, nothing obsolete, no unused type, unique type names, one type per file, no `dynamic` and no null-forgiving `!` outside tests, the build settings and the names of migration scripts.
- This repository's own (in `suwgate.yml` or `Suwageval.Gate`):
  - the chart: `helm lint` and `helm template` with the 63-character limit on annotation and label names (`Suwageval.Gate/scripts/chart.sh`);
  - the plugin's session hook gives an agent's repository the Suwageval loop (a step of `suwgate.yml`); manifests and skills are sound (`ClaudePluginTests`);
  - the order of the features inside an area, and a sub-feature used by neither its feature nor its siblings (`ServerContractsTests`); the CLI's layers and areas (`CliContractsTests`);
  - no test class starts the server in a field (`ClassServerTests`); a linked worktree's tests never use the main checkout's database (`TestDatabase`);
  - the server's image copies every project it builds from (`ServerImageTests`); no two web modules in one folder differ only in letter case (`WebModuleNamesTests`);
  - a file `criteria.json` reads as prose is named whole and holds no test (`CriteriaExamplesTests`);
  - eslint: the import boundaries of the web (below), a request in an effect goes through `api/useRequest.ts`, a switch over a union names every member.

## Rules this repository switches off, and why

| Rule | Where | Why |
| --- | --- | --- |
| `JSON002` | all C# | it asks for a `/*lang=json,strict*/` marker on every string that looks like JSON; the build never reports it, and as a fixer it made `just fmt` rewrite tests whose JSON is the expected wire text |
| `CA2100` | the test projects | the SQL a test builds (a scratch schema's name, a database to recreate) is its own, never input |
| `CA1716`, `CA1056` | the contracts and the SDK | "Event" is the domain word, not the keyword a VB or F# consumer would trip over; a URL arrives as the text the file holds, checked where it is used |
| `RS0030` | `Suwageval.Cli/Program.cs` | the entry point of the CLI is its one door to the console: it hands the console on as a reader and writers |

## Import contracts: which part may use which

A part may use the parts below it, never above it or beside it. "Below" means more basic. The order is data in `layers.json` for the server and the CLI, and `boundaries/*` in `Suwageval.Web/eslint.config.js` for the web; a dependency against it fails with the types involved. The check reads compiled code: a `const` or a `nameof` leaves no trace there, a type used in a signature, a field or a call does.

- **Areas.** An area (`Evaluation`, `Monitoring`) groups the features of one product area: one entry in the top order, with an order of its own inside. An area never uses another area. Features every area needs stand below the areas and never use one; what a second area needs from the first moves down into a shared feature. `Api` and the parts above the areas compose them.
- **The CLI** is layered the same way. The commands of an area are siblings, none uses another; what two share moves down. Command names stay flat on purpose (`suwageval run`): evaluation is the daily work, so only the code follows the areas, and `HelpSections` shows them as sections.
- **The web.** A feature of an area imports itself, the shared folders and the features of its own area named in an explicit policy; a shared folder never imports an area. A new web feature is a folder the rule already covers.
- **Projects** point one way (`projects` in `layers.json`): the CLI and the server know the contracts and nothing of each other; only the server's tests know the CLI, for the end-to-end tests.
- **A contract change is a design change.** Say in the change why the new edge exists.

## How code is split

The app grows by features: the code that makes one feature work sits in one folder on each side, named in the users' terms (scenarios, compare, trend), not by technical kind. A change to one feature then touches one place per side, and a feature can be read, moved or deleted as a whole. The word is the same on every side; the tree need not be: the web cuts by screens, the CLI by commands, the server by routes and data.

- A new capability starts as a new folder or goes into the feature it belongs to, never into a shared bucket. Shared code is earned by the second feature that needs it and is named after what it is (`Output/`), not after who uses it.
- When a feature grows, the signs are content, not file counts: a second set of routes, a group of files that change together with a shared name prefix, a part the web or the CLI already has as a folder of its own.
- A part built on its feature and meaningless without it becomes a sub-feature, a folder inside it: it uses its feature and everything below, and its feature and siblings never use it. One level deep. A part that stands on its own becomes a sibling feature with its own layer.
- Server: a feature is a folder and a namespace; with several concerns it splits by role (`*Endpoints` with the routes `Api/ServerApp.cs` maps, `*Store` with the SQL, the records). Types are `internal`; tests see them through `InternalsVisibleTo`.
- A record the API sends or receives is declared once in `Suwageval.Contracts` and is a contract with someone outside; a row from our own SQL is not. A store returns its own row type and the endpoint maps it, so a reader can tell whether changing a type changes the API.
- An operation's logic lives once, in the store or an operations class; the endpoint only maps it to HTTP, and a problem the caller can fix is a Problem Details whose `detail` says what to do.
- Queries are plain SQL with `@name` parameters, mapped by Dapper. No ORM and no SQL generator: the SQL a reader sees is what PostgreSQL runs.
- A closed set of values is a type of its own: an `enum` on the server, serialized by name, a union of string literals on the web.
- C# conventions on the server, the web's on the web; camelCase in JSON, snake_case tables and columns. C# tests mirror the server's folders, since they cannot sit beside the type.

## Decisions the code relies on

What a reader cannot see in the code, and the code would look wrong without.

- **Server.** Routes have no `/api` prefix: the edge (the web's nginx, the cluster's ingress) strips it. The OpenAPI build starts the app, so start-up must not touch the database. Responses omit unset fields with options kept apart from `ContractJson.Options`, which also serializes what gets hashed. The agent's contract is read and registered before anything is queued.
- **Runs.** A worker claims a run with `FOR UPDATE SKIP LOCKED`; one server replica is assumed (more would need a worker heartbeat). The simulated user's temperature is above 0 on purpose: samples differ, and the pass threshold makes the result repeatable.
- **Database.** A pooled connection is tried before it is handed out, or the first request after a database restart fails with 57P01. grate copies the scripts into temporary folders it never deletes, so they are removed by hand. Some row types use properties, not constructors: Dapper cannot match a constructor to a `text[]` column.
- **Models.** The OpenAI client needs a key to build, so a model that asks for none gets a placeholder. A model can change its answer without a commit here: the daily live check is what notices, the one other command of the server's image, run by the chart's CronJob.
- **CLI.** It reads the server's answers leniently (a newer server may add fields), the files a person writes strictly. JSON output is ASCII-escaped: a console that is not UTF-8 would break typographic quotes. The page size never changes between requests, because the server pages by number. Ctrl+C during the `run --wait` question ends the process at once (System.CommandLine alone would wait two seconds). System.CommandLine's help builder is internal, so the root help is written by hand.
- **One number in three places.** The comparison's limit of runs and the printed page's width are literals in the server, the CLI and the web, which tests keep equal (`PrintMaxRunsTests`); the page width is A4 landscape less the 10 mm `@page` margins of `print.css`, at 96 dpi.
- **Web.** StrictMode runs effects twice in development, so the first request is aborted and its result ignored. What is folded on the screen stays in the page, hidden, so `print.css` can print it. The Problems cards stand above the filters, so the view waits for their first answer instead of pushing an open list off the screen. The navbar draws its nesting by hand, because Mantine turns a click on a NavLink with children into a toggle.
- **Images.** The build context is the repository root (`global.json` and the `Directory.*.props` live there). Restored packages stay in the image layer, not in a cache mount CI would start empty. nginx resolves the server through a variable, so a recreated server container does not leave a cached address answering 502; on the cluster `API_UPSTREAM` is the full service name. `/healthz` does not depend on the API; `index.html` is never cached, the hashed assets forever. `envsubst` fills only its two names, so nginx's own `$host` survives.
- **Chart.** `image.tag` has no default: the platform repository sets it, a missing tag stops the deploy, and a code commit never deploys by itself. `enabled: false` renders nothing, so Argo prunes the release while the namespace, Secrets and database stay. The smoke test and the live check never retry: the script retries transient failures itself, and a retried daily alarm would only ring twice.
- **The SDK's release.** Only `just agent-publish` starts it, because a version on nuget.org cannot be deleted; the trusted-publishing policy names `agent-sdk.yml`, so the file is never renamed alone. `nuget.config` names nuget.org only: a second source makes central package management raise NU1507, which warnings-as-errors turns into a failed build. The SDK targets net9 as well because the strict JSON options of `ContractJson` need it.
